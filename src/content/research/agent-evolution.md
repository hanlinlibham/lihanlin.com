智能体怎样持续承担真实工作，又怎样让成果成为下一次工作的可靠输入？这是这个系列要研究的问题。

2026 年 11 月启动。当前整理了比较对象、分析框架和六个研究主题，后续沿这条路线展开。各项目的出发点是依据公开定位和机制所作的归纳；产品目标、已验证的运行事实与未来推断分别讨论。

## 01 · 智能体为什么形成不同的产品形态

用户交给智能体的可能是一个问题、一项任务、一类职责，也可能是一个长期目标。委托内容不同，系统需要保存的状态、可以采取的行动和完成标准也不同。

这一篇先建立共同问题：

- 用户离开后，工作靠什么继续？回来后，又靠什么接上？
- 上下文围绕人、讨论、角色、任务，还是业务对象组织？
- 一次工作结束，留下什么？下一次怎样使用它？
- 什么可以持续执行，什么变化需要人重新决定？

分析从用户困难与目标出发，再看交互入口、任务状态、记忆、权限和交付如何配合。

## 02 · 五条路径的出发点与目标

每个案例沿同一条线展开：用户遇到什么问题 → 如何委托 → 系统怎样推进 → 何时需要人 → 结果留下什么。以下是研究切入点。

### Muse：围绕个人与长期目标

**出发点：** 一个人的事务散落在不同应用里，长期目标需要不断协调和推进。

**目标：** 理解个人偏好与目标，在授权范围内持续处理事务。重点看持续关系、跨应用行动、个人记忆和敏感操作确认，分析便利性与授权复杂度如何相互影响。

[Meta 官方介绍](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)

### Grok Bot：围绕可委托的角色与流程

**出发点：** 工作跨越邮箱、浏览器和业务工具，用户仍需搬运信息、操作软件和协调步骤。

**目标：** 把一类工作交给长期存在的 Bot，让多个 Bot 分工、交接并复用流程。重点看持久云端电脑、示范学习、技能和例行任务，以及分工是否真正减少人的协调负担。

同一用户的 Bots 共享云端电脑上的文件、浏览器会话与应用登录；角色分工和权限隔离需要分别分析。这里的 Grok Bot 是独立执行产品，X 上的 `@bot` 是任务入口，与公开回复账号 `@grok` 区分。

[产品介绍](https://x.ai/news/introducing-grok-bot) · [运行与共享环境](https://docs.x.ai/grok-bot/overview) · [X 任务入口](https://docs.x.ai/grok-bot/tag-on-x)

### Claude Tag：围绕团队正在发生的讨论

**出发点：** 团队上下文已经存在于讨论中，调用 AI 时却经常需要重新解释和搬运材料。

**目标：** 让团队在工作发生的地方委托 AI，共享进展并接续讨论。重点看 Slack 频道与线程、异步交付、主动跟进，以及工具和记忆如何受可见范围约束。

[Anthropic 官方介绍](https://www.anthropic.com/news/introducing-claude-tag)

### DeepSeek Super-agent：围绕持续推进的任务

**出发点：** 工程工作由多种事件推动，会并发、等待和中断，也需要跨会话继续。

**目标：** 减少人维持上下文、派工和追踪进度的负担。重点看事件进入、任务分派、执行会话、等待与恢复，以及结果如何回到原讨论。

公开研究原型聚焦 GitHub 编程协作，可接入飞书。设计文章、内部实现和公开原型的范围分别讨论；独立目录与会话不直接视为安全沙箱。

[官方研究原型](https://github.com/deepseek-ai/dsh-superagent-prototype) · [行为原则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/000-philosophy.md) · [部署与隔离说明](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/006-deployment.md)

### AbleWork：围绕研究对象与知识积累

**出发点：** 研究材料、个人判断和 Agent 成果不断增加，需要进入后续工作，并保留来源、版本和权限。

**目标：** 支持研究协作，让成果成为可更新、可追溯、按权限复用的知识。重点看报告、主题和指标旁的就地委托，持续关注，以及成果发布、知识编译和后续消费如何连接。

AutoWiki 作为知识编译组件参与其中；平台宿主负责身份、材料、任务、权限与发布。研究将分别说明已经运行的应用、历史完整验证和仍待验证的部分。

[本站 AbleWork 项目介绍](/projects/ablework/) · [AutoWiki](/projects/auto-wiki/)

## 03 · 横向比较：相通的机制与不同的选择

五个项目有重叠能力。比较关注各自主要围绕什么组织工作，以及这些选择带来的收益、成本与边界。

- **持续关系：** 围绕个人、角色、团队讨论、任务还是研究对象？
- **工作接续：** 怎样保存目标、约束、进度、等待条件与成果版本？
- **协作责任：** 谁分派、谁交接，谁对结果负责？
- **记忆与知识：** 保存偏好、经验、任务历史，还是正式领域知识？怎样更新与撤回？
- **行动权限：** 什么可以自行继续，什么需要重新授权？
- **完成标准：** 回答、业务工具更新、PR、研究成果与知识发布各自怎样验收？
- **成本与打扰：** 何时调用模型、何时通知、何时保持安静？

共同采用事件触发或异步执行，不代表具有相同的安全保证。目录、任务系统和检索服务也承担不同职责，需要看它们如何结合。

## 04 · 对后续智能体形态的影响

这一篇根据案例提出推断，并说明成立条件。几种形态可能长期并存：

1. **个人持续代理：** 长期理解一个人的目标、偏好与约束。
2. **可委托的数字团队：** 多个角色分工，让用户主要处理关键决定。
3. **嵌入协作空间的 Agent：** 在讨论和业务对象中承接工作。
4. **支撑持续任务的运行系统：** 处理并发、等待、恢复与交付。
5. **积累领域知识的应用平台：** 将工作成果转为下一次工作的可靠输入。

重点考察它们怎样组合，以及组合后新增的协调成本、权限复杂度和错误累积问题。未来判断要接受实际任务、长期使用和成本数据的检验。

## 05 · AbleWork 当前怎样应用这些机制

用研究场景检验前面的分析，计划沿以下用户路径展开：

- 阅读报告、查看指标或讨论主题时，就地委托 Able，结果回到对应工作面。
- 明确建立研究关注后，后台周期检查，在有变化时准备结果。
- 一人的研究成果发布后，进入另一人的后续问题，读取时核对来源版本和权限。
- 根据阅读导航与正式知识积累的不同需求，选择梗概或完整编译。

当前日常增量、历史完整编译、个人实例向公共层提交候选，是需要分别取证的路径。研究将解释每条路径已经证明了什么，哪些部分仍缺后续采用或验收证据。

公开材料聚焦架构、交互与设计选择；内部业务内容、用户身份及私有运行细节不进入本系列。

## 06 · AbleWork 的取舍与后续结合

最后回到产品决策：哪些经验适合研究工作，怎样验证引入后的价值？

- 从 Muse 的持续关系体验出发，怎样减少用户维护上下文的负担？
- 从 Grok Bot 的流程复用出发，怎样减少重复操作，同时控制角色数量与协调成本？
- 从 Claude Tag 的原处协作出发，怎样保持讨论、交付、读权与署名之间的关系？
- 从 Super-agent 的任务组织出发，怎样处理长期研究中的等待、变化与恢复？
- 什么成果只需梗概，什么值得完整编译？公共候选何时可以被正式采纳？

后续以实际任务检验选择：工作能否接续，成果有没有被再次使用，来源与权限是否有效，以及用户为此付出了多少注意力和操作成本。
